# 共享 index 下的提交纪律：`git commit --only`（2026-09-29 两次实测事故）

## 两次事故，同一个病根

**第一次**（有删除版，**靠门挡住了**）
`git add -A` 连带暂存他窗文件 → `check-commit-deletions.sh` 拦下整个提交。
⇒ 那个门**确实有效**，因为删除有确定签名。

**第二次**（无删除版，**门完全看不见，核对我做了也通过了**）

```
git diff --cached --name-only | grep -vE "<我的文件>"   →  ✅ 无混入
git commit                                              →  提交里 4 个文件
```

另两个是 `l1_action/nt_media/{audio_decode,thumbnail}.rs` ——
**另一窗口 25 行在途工作被我带进账**。

⇒ **失效的不是纪律，是纪律的执行窗口。**
共享 index 上「核对」与「提交」**不是原子的**，
中间任何时刻别人都能改写暂存区。

## ⛔ 为什么 pre-commit 门防不了（实测，非推演）

第一反应是加一个「暂存数 vs 提交数」的比对门。
写完在 `/tmp` 造 scratch repo 实测 **git 到底会不会把路径传给 hook**：

```
git commit           → HOOK-ARGS(0): []
git commit --only x  → HOOK-ARGS(0): []
git commit -a        → HOOK-ARGS(0): []
```

**三种方式都只传 0 个参数。** hook 看不到「我打算提交什么」
⇒ 任何基于「暂存数 vs 提交数」的门**必然恒失败**：
对普通 `git commit` 永远退 1（堵死一切提交的假门），
对 `--only` 也看不出差别。

**⇒ 我写过这样一个门、接进 pre-commit、语法检查通过，
自测时才发现它无效，已删。**
留一个「看起来在防事故、实际恒失败或恒阻塞」的门比没有门更危险 ——
下一个人会以为风险已被覆盖。

## ✅ 真解法：把原子性交给 git 本身

同样在 scratch repo 实测竞态（核对后、提交前，别人 `git add`）：

| 方式 | 提交内容 | 他窗文件 |
|---|---|---|
| `git commit` | mine.txt + **other.txt** | ⛔ 被带进账 |
| `git commit --only mine.txt` | **mine.txt** | ✅ **仍在暂存区，内容完好** |

`--only` 由 git **内部原子**限定路径，**结构上**不存在那个竞态窗口。

## 纪律

```bash
git commit --only <我的文件...> -F /tmp/msg.txt
```

**不再用** `git add <文件>` + `git commit`。
独立 worktree / 独占 index 时无此竞态，但统一用 `--only` 成本为零。

## 补救（若已误提交，不丢内容）

```bash
git reset --soft HEAD~1                    # 内容全回工作区/暂存区
git restore --staged <他窗文件>            # 退回工作区未暂存，内容完好
```

⛔ **不 amend、不 `reset --hard`** —— 那会毁掉他窗未提交的改动。
本次即用此法恢复：他窗 25 行完好退回工作区，
他窗随后自行提交了溯源 `01bb8483`。

## 元教训

**「我核对了」不等于「我验证了核对有效」。**
两次事故里我都**执行了核对纪律**，第一次纪律本身不够（`add -A`），
第二次纪律**执行到位但依然失效** —— 因为它**在时间上不是原子的**。

⇒ 检查纪律的**失效模式**与检查纪律**是否执行**同样重要。
⇒ 门只能覆盖**有确定签名**的失效模式（删除有，改动没有）；
   无签名的失效模式要靠**结构性保证**（`--only`），不能靠自觉。
