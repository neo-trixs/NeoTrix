## §3 能力清单（每项含我方 `文件:行` 证据）

### 3.1 ⭐⭐ 不要建本地消息全文索引（**反向结论，价值最高**）

**他们没有本地索引 —— 这是设计选择。** `SearchController::SearchRequest`
就是**服务端 API 方法本身**；全库无 FTS/BM25/倒排/trigram；
`SearchResult` 只是「服务端返回的 id 列表」，客户端按 id 从本地缓存水合。

⇒ **直接回答了我们最该问的问题：不要建。**
索引要维护、要与删除同步、要处理权限失效 —— 而服务端搜索已解决。

**⇒ 我方现状：✅ 已正确。** `messages` 表只有 `(convo_id, created_at)` 索引，
**无 `text` 索引** ⇒ **保持现状**。
⓰ 上一轮把「无本地搜索」判为 ❌ 缺失，**这个判定是错的** —— 缺的是**服务端搜索接入**与交互层，不是索引。

值得抄的三个工程设计（与「谁搜」无关）：
1. **结果集 = 稀疏 id 列表 + `aroundId` 前后切片** ⇒ UI 永不持有全集
2. **按整个查询结构做缓存键**（`Query` 带 `operator<=>`，可直接做 map key）⇒ 重复搜索零成本命中
3. **去抖层**（输入延迟与请求频率解耦）
⓰ 另记一条易踩的：**「服务端分页 ∩ 本地缓存」的重叠必须显式处理**（他们叫 `noSkipRange`），
否则用户会漏看已在本地的那几条。

### 3.2 入站差量同步：缺口检测与乱序缓冲

**他们怎么做**：`PtsWaiter` 维护 `_last`（见过的最大 pts）与 `_count`（累计计数）：
- `_last == _count` ⇒ 连续，**立即应用**
- `_last > _count` ⇒ **有缺口** ⇒ 等一个短超时，赌缺口那条会在窗口内自己到达（乱序在途）
- `_last < _count` ⇒ 计数溢出 ⇒ 立即短轮询
乱序更新**先缓冲**、缺口填上后**回放且不再重复校验**；幂等靠 **pts 单调**（`pts <= _good ⇒ 丢弃`）。
退避阶梯 `1,2,3 → 1000 → ×2 → 封顶 64s`，**每渠道独立计数**，成功即复位。
「重试的原因」被**显式建模为类型**（`ChannelDifferenceRequest` 三态），
而不是隐含约定。

**我方现状**：⚠️ 游标 `offset` **只在适配器内存、明文规定不落库**（设计律，有文档论证），
靠 `channel_seen` 去重表兜底。**缺缺口检测、乱序缓冲、入站退避三件。**

⚠️ 顺带发现一处**我方**的健壮性缺口（**未实证，仅静态推演**）：
`fetch` 的 `offset` 推进依赖批内 `update_id`；若整批都缺该字段，**游标不推进 ⇒ 该批无限重放**。
他们用「pts 单调 ⇒ 丢弃」正面挡住了这类。⏳ **立项前应先写测试确认可达性**。

### 3.3 草稿：统一键空间（且**先决策再动手**）

**他们怎么做**：本地草稿与云端草稿**不是两个系统，是同一个 `int64` 键空间的两个区间**
⇒ `isLocal()`/`isCloud()` 退化成区间比较 ⇒ **结构上「本地/云端冲突」不可能发生**。
冲突裁决是**三重守卫的合取**，第一条就是
**「用户正在这个输入框里打字 ⇒ 忽略一切外部草稿」**。
「保存中」抑制用**引用计数**而非布尔（多次保存会重叠）。
流式草稿的「停止」是**终态**（从活跃表移除 + 永久 id 黑名单）⇒ **停止后无法复活**。

⭐ **战略判断（比技术细节重要）**：**Bot API 没有草稿接口**；
云端草稿与流式草稿都是**用户 API 专有**。
⇒ 走 Bot API 则**云端草稿拿不到** ⇒ 建议**只取「本地草稿」这一半**，
云端与流式标记为「**不做，除非将来上用户 API**」。

**我方现状**：❌ `rg -c -i draft` 在 `crates/neotrix-neobot/src` ⇒ **零命中**。
`draft` 目前只是 React `useState` ⇒ 刷新/崩溃即失。

**⏰ 可无条件采纳的一条**（与平台无关，纯 UX 正确性）：
**用户正在输入时，任何外部来源的内容都不许覆盖输入框。**

### 3.4 发送队列与重试

**他们怎么做**（⭐ 与我们认知的差别最大）：
- **没有独立 outbox 队列 —— outbox 就是消息列表本身**。发送状态是消息项上的两个 bit。
  ⓘ 好处：不存在「两个队列要保持一致」这个经典问题。
- 幂等锚点是客户端生成的 `randomId`，且它**穿过更新路径**：回执带这个 key，
  且「是否已存在」在变更**前**捕获并**显式下传**给消息项，让它自己决定要不要重放
  ⇒ **显式幂等，不靠事后比对**。
- 失败路径同样带 key，且**断言 key 非零** ⇒ **失败必须能关联到具体那一次尝试**。
- **传输层与语义层分离**：传输层管退避与重发，**消息级失败不重试**；
  语义层只对「文件引用过期」这一类做**有界重试**（刷新后**仅当确实变了**才重试一次），
  且用一个 `refreshed` 标志**在结构上排除递归重试**。
- 状态迁移带**运行期断言**（`Expects(...)`）。

**⭐ 我方有两套 outbox，语义不同**（上一轮只知道一套）：

| | `pending_deliveries`（渠道投递） | `outbox`（agent ledger） |
|---|---|---|
| 时间退避 | ⛔ **无 `available_at` 列** | ✅ 有 |
| 原子认领 | ⛔ **无 `claimed`** | ✅ 有 |
| 放弃上限 | ✅ `MAX_SEND_ATTEMPTS = 3` | ⛔ 无（靠毒行丢弃） |
| 毒行处理 | ⛔ 无 | ✅ 有，**且带成文论证** |

⓰ **我方比他们强的一点**（须明说）：ledger outbox 的毒行丢弃**写了理由**
（「payload 一旦写入即不可变 ⇒ 解析失败永远不可能变可发 ⇒ 重试不是恢复」）
—— 这正是他们用代码结构（`refreshed` 标志）表达而**未加文字论证**的那条原则。

⛔ **两处必须修**：
1. `pending_deliveries` **无时间退避、无 `claimed`** ⇒ 失败后秒级重试 3 次即放弃；
   且若 drain 与别处并发投递同一行，**会重复发送**（ledger outbox 用 `claimed` 防住了）。
2. ⛔ **文档与实现不符**：`lib.rs` 声称「outbox（attempts、available_at 退避）」，
   但该说法**只对 ledger outbox 成立**，对 `pending_deliveries` **不成立**。
   ⇒ 这是一条**会误导下一个 agent 的陈旧声明**（`R-SCAN-3` 意义上的门记录失真）。

## §5 明确**不建议**做

| 项 | 理由 |
|---|---|
| 完整 pts/getDifference 差量同步 | 需先确认**是否存在多端并发写同一会话**的真实场景；无场景即为不存在的问题写代码。可先只做第 5/6 项 |
| 独立 outbox（把消息列表当队列） | 我们的持久 outbox **更适合多进程恢复**（他们那份是内存表，只补上下文、不承担恢复职责） |
| 媒体缩略图/转码管线 | 那些管线服务于**我们不存在的功能**（Stories、流式播放）⇒ 会闲置 |
| 任何形式的代码移植 | ⛔ GPL-3.0 + 传染 |

## §6 ⏳ 明确**无法确定**（⛔ 不猜）

- ⭐ `lib_storage` 私有 ⇒ **本地草稿的实际字节布局、加密如何介入，不可知**
- ⭐ `lib_rpl` 私有 ⇒ `idsSlice` / 稀疏 id 切片的**分页窗口算法不可知**
- 稀疏 id 列表的**排序键**未读（假设按消息 id 有序，未证）
- 我方 `pending_deliveries.id` 的生成规则**未查** ⇒ 「无幂等键贯穿」这条**仅限「失败关联到具体尝试」这个维度**；
  若该 id 本身已由意图派生，可能已有部分覆盖 ⇒ **立项第 2/3 项前应先核实**
- 我方 `fetch` 游标死循环风险**仅静态推演，未构造真实输入实证**（`R-SCAN-2`）
