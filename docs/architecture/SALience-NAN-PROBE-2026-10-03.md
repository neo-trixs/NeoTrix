# 批 2 探针结果：**我的假设被自己的实验推翻**（2026-10-03）

> 承诺过「先构造 NaN 输入实测，再决定改不改」。实测结论是**不改**。
> 本篇记录推翻过程，因为**推翻比结论更有信息量**。

## 目标
`decay_forgetting/salience.rs:76`
```rust
let access_factor = (entry.access_count() as f64 / self.max_access_count).min(1.0);
```
⭐ 该行有个 `min(1.0)`，而 `min` 是**本会话已重点关注**的饱和/静默退化形状 ⇒ 故拿它当批 2 的探针对象。

## 前置检查（这一步就救了我一次）
`:63-65` `with_max_access_count` 有 `max.max(1.0)`；`:59` `new()` 默认 `100.0`
⇒ 我**原以为**的 NaN 源（除零）**被守卫挡住了**。
⇒ 但 `:51 max_access_count: f64` 是 **`pub`** ⇒ **可绕过守卫直接赋值**。

## 独立实验（不依赖坏掉的共享树，故用 10 行独立程序验证语言语义）
```
0.0/0.0        = NaN   is_nan=true
NaN.min(1.0)   = 1     is_nan=false     ← NaN 被静默转成「最大值」
(50/0).min(1.0)= 1     ← 30 天前 acc=50 的对照组，也是 1.0
partial_cmp+Equal 排序⇒ ["fresh", "old"]
total_cmp 排序      ⇒ ["fresh", "old"]     ← 两者结果相同
```

## ⛔ 三条被推翻的断言（我动手前的判断全是错的）
| 我以为 | 实测 |
|---|---|
| NaN 会漏进排序，导致错序 | ⛔ `.min(1.0)` **把 NaN 吃掉了**（Rust 的 `min` 返回非 NaN 那个）⇒ 排序里**没有 NaN** |
| 「全新条目」会被抬到最高显著度 | ⛔ `acc=50` 同样得 1.0 ⇒ **全体并列**，新条目并不特殊 |
| 本文件该改 `total_cmp` | ⛔ **不需要** —— 没有 NaN 抵达比较器 |

## ⭐ 真实问题（**另一个形状**，且确实存在）
`max_access_count` 为 `pub` ⇒ 可绕过 `.max(1.0)` 守卫。
一旦被写成 `0.0`，对**任意** `access_count`：
* `acc > 0` ⇒ `inf.min(1.0)` = **1.0**
* `acc == 0` ⇒ `NaN.min(1.0)` = **1.0**
⇒ **`access_factor` 恒为 1.0 ⇒ 该维度对所有条目完全失去区分能力。**

⭐ 这与我本会话修掉的 `effective_salience` 饱和缺陷**同型**：
都是「一个上限/系数把整个维度压成常量」，而非「某个条目被算错」。
——**这一类才是值得普查的形状：不是 NaN，而是「维度被压平成常量」。**

## 建议的最小修法（**本轮未落代码**）
把 `:51` 的 `max_access_count` 改为**私有**，强制经 `with_max_access_count`
（它已有 `.max(1.0)`）—— 守卫已存在，只是能被绕过。
⛔ 未落盘的两个理由：
① 改字段可见性属**跨模块 API 变更**，须先反查消费方（`grep` 只找候选，不下结论）。
② 共享树当前**被别窗重构打断**（`nt_dialogue_tui` 缺失、`cli_free_source.rs` 编译错）
   ⇒ **无法验证**，而我的事故记录里刚写死「批量/未验证改动不可接受」。
