## 一、它主张什么
把**执行控制**当成一个**独立任务**显式化：
- **worker** 只做任务级计算
- **controller** 做四件事：整合「这次运行已确立了什么」→ 探索下一个选项 →
  **评估每个选项在剩余预算下值多少** → 用持久记忆里的上下文派发
- ⭐⭐ **「两次决策之间，controller 只携带一个紧凑的运行摘要，而不是重放完整历史。」**

**结果**：ProgramBench（程序重建，长程 agentic 能力）
| | meta-reasoning | 直接控制 |
|---|---|---|
| GPT-5.5 | **71.5%** | 58.0%（Codex） |
| Opus 4.8 | **67.2%** | 65.5%（Claude Code） |

其他基准（抽象推理 / 多域长程 / 证明生成）：跨 3 个前沿模型平均 **+3.6 ~ +4.2**。
⭐ **「在直接控制停滞的预算区间上，它仍在改进；但其开销在小预算下会**有害**。」**

## 二、⭐⭐ 它打在我们身上的两句

### ① 「controller 携带**紧凑摘要**而非重放全历史」
⇒ 我们有对应物：`nt_core_context/`、`nt_smart_context.rs`、`context_assembly.rs`。
⇒ ⭐ 但**我们没有验证**它们是否真的做「压缩摘要」而不是「截断/拼接」。
⇒ 按前置门第①问：**危险面未确证 ⇒ 本篇不提改造方案**，只登记待查。

### ② ⭐⭐ 「**开销在小预算下会有害**」—— 这是一条**可证伪的约束**
⇒ 它直接命中我们的 `EMERGENCE-PLAN`：涌现判据本身是**控制开销**。
⇒ 若在小预算下开销有害 ⇒ **我们的门与检测器必须有预算下限**，
否则「涌现」信号会被开销淹没。
⇒ 已据此新增失效条件 **`EMERGENCE-PLAN` §6.9**。

## ⛔ 附：本篇的 commit message 被我自己弄坏（第 5 次反引号事故）

`git commit -m "... \`resonance.rs\` ... \`7dda1e88\` ..."` ⇒ zsh 把反引号当**命令替换**执行 ⇒
那两个标识符在**提交说明里**被替换成空输出。

⇒ **本文档内容不受影响**（文件用 `<<'MDEOF'` 引号定界heredoc 写入，安全），
受影响的是 `-m` 后面那个**双引号**字符串。

### ⛔ 因此形成的硬规则（本会话已犯 5 次，必须固化）
> **⛔ 绝不在 `git commit -m "…"` 的双引号里使用反引号。**

| 正确写法 | 说明 |
|---|---|
| `git commit -F <文件>` | ✅ **首选** —— 用 `<<'EOF'` heredoc 写文件，**引号定界 ⇒ 不展开** |
| `git commit -m $'…'` | ⚠️ ANSI-C 引号，反引号**仍会**被当命令替换（实测） |
| 干脆不用反引号 | ✅ 次选 |

### ⛔ 为什么这次没造成更大损失
因为**文件正文**走的是 `cat > file <<'MDEOF'`（引号定界 ⇒ 不展开），
而只有 `-m` 那段用了双引号。
⇒ **同一条命令里两种写法混用**才是这次出问题的原因 ——
**一致性比技巧重要**：**要么全用 `-F` 文件，要么全程不写反引号。**

### 记录一下这个错误的性质
本会话前 4 次（`check-disk.sh` 的 `cargo clean`、`resonance.rs` 的 `command not found` 等）
都是**真会造成损害**的那种；这一次目标无害（命令不存在 ⇒ 报 not found）。
⇒ ⭐ 但**5 次里 0 次是我事先想到的** ⇒ 它不是「不小心」，是**必须用规则挡住的东西**。
