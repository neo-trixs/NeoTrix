## 0. ⭐ 核心发现：五类问题只有**一个**共同根因

D2 五片（D2-a…D2-e）的表面信号各不相同，但**根因同一**：

> **代码「看起来在工作」，实际与真实状态无关。**

| 片 | 门报告的信号 | 真实问题 | 共同根因 |
|---|---|---|---|
| a `l0_substrate` | 2 个零读点字段 | 策略是**无状态 unit struct** ⇒ 结构上拿不到 `config` | 声明 ≠ 可达 |
| b `nt_io_inference` | 2 个零读点字段 | `detect()` **零系统调用**，恒返回 M5/16GB | 声明 ≠ 真实探测 |
| c `nt_shield/defense` | 13 个零读点字段 | `reasoning_safe: true` **硬编码字面量** | 声明 ≠ 真实结论 |
| d `nt_memory_kb` | 7 个零读点字段 | 权重在 **RRF** 架构下**无语义对应** | 声明 ≠ 架构可承载 |
| e `background_loop` | 9 个零读点字段 | `compute(true,kb,true,true)` ⇒ **75 分恒定** | 声明 ≠ 真实信号 |

### ⭐ 为什么现有门全部抓不到

现有 33 个门覆盖的是「**有没有用**」（`check-dead-config-flag`、`check-unwrap`）
与「**声明得对不对**」（`check-doc-drift`、`check-claims-numbers`）。

⛔ **没有一个门问「这个值是真算出来的，还是写死的」** ——
而这正是五片的**全部**问题所在。

⇒ **唯一需要新建的门：`check-fake-signal`**（见 §2）。

## 1. 五类的处置方案（逐类，含判据）

> 每类都必须先回答同一个问题：**这个值声称自己是什么？它真的是吗？**

### 类型 1️⃣ 声明 ≠ 可达（结构性不可读）

**症状**：字段属于**无状态 struct**（`pub struct X;`），其方法拿不到 `config`。

**判据**：读 `impl` 块的方法签名 ⇒ 参数列表里**有没有**承载配置的字段/引用。

**处置**：⛔ 不删字段（规格有价值）；✅ 把配置**注入**进策略构造
（`RecoveryOrchestrator::new()` 处 `config` 本就可用）。

✅ 已落地：`581266bd`（`enable_checkpoint` / `enable_semantic_fallback`）

---

### 类型 2️⃣ 声明 ≠ 真实探测（伪检测）

**症状**：函数名叫 `detect` / `probe` / `measure`，内部**零系统调用**。

**判据**（instrument，非推断）：
```sh
grep -nE 'sysctl|Command::|/proc|cpuid|target_os|uname|std::fs' <file>
#   零命中 ⇒ 该「探测」函数没有探测任何东西
```
**二值判据**：`detect()` 两次调用结果**完全一致** ⇒ 它是常量。

**处置**：
- ⛔ 不删（参考资料/benchmark 数值来源真实，有价值）
- ✅ 在**函数文档**与**模块文档**两处留痕（模块文档的承诺最容易骗过人）
- ⭐ **写测试固化「它是常量」** ⇒ 将来接上真探测时该测试**会失败** ⇒ 提醒更新

✅ 已落地：`bf979ed3`（`apple_silicon::detect`，416 行零系统调用）

---

### 类型 3️⃣ 声明 ≠ 真实结论（硬编码的安全/健康结论）

**症状**：字段名读起来像**已验证的结论**（`*_safe` / `*_compliant` / `*_ok`），
实际是 `true` 字面量。

**判据**：
```sh
grep -nE '<field>\s*:\s*(true|false)\s*[,}]' <file>
#   命中 ⇒ 该字段被**写入常量**；再确认它是否有其他赋值点
```
**承重判据**：**对照测试** ——
证明「同模块内**真计算**的字段**会随输入变化**」，
才能确立「这个字段硬编码」的结论是相对而言的。

**处置**：⚠️ **绝不可**为了让分数/结论"看起来合理"而改成「看起来在算」。
✅ 逐字段标注真实/未测量；未测量的**保留字面量**但显式声明「⛔ 不可当作已验证信号」。

✅ 已落地：`7d8c625a`（`CoreVerification`）、`1a1ed01d`（`LoopReadyScore`）

---

### 类型 4️⃣ 声明 ≠ 架构可承载（规格与实现冲突）

**症状**：配置字段语义清晰（`rerank_weight_fts: 0.3`），
但现役实现在**算法层面**没有对应概念。

**判据**：读**真正被调用的**实现（⛔ 见下方「同名异型」），确认其融合/决策算法。

**处置**：
- ⛔ **不可**为了「接线」而替换现役算法（会回归质量，且破坏既有修复）
- ✅ 逐字段定性 + 给出两个正解（增强算法 / 删除过时字段）+ **标明需 owner 决策**
- ⚠️ 记录**通道数不符**等硬证据（`fuse_weights: [f64;4]` vs 实现 3 通道）

✅ 已落地：`26afd487`（RRF 无浮点通道权重语义）

---

### 类型 5️⃣ 声明 ≠ 真实信号（权重恒定）

**症状**：加权评分函数**接入了硬编码参数** ⇒ 权重表是摆设。

**判据**：
```sh
grep -nE 'compute\([^)]*' <file>   # 看实参是否为字面量 true/false
```
**承重后果**（必须一起查）：恒定的高分会让**下游门永远绿** ——
如 `handlers_ok` 恒 true ⇒ 分数永远 ≥75 ⇒ 自治梯度永远 ≥L2 ⇒ **永不降级**。

**处置**：找**handle 上确实存在的真实信号**接线；
⛔ 若本仓**无**该测量 ⇒ 保留字面量但**显式标注「未测量」**，
⛔ **不**伪造接线（假分数比无分数更危险）。

✅ 已落地：`1a1ed01d`

## 2. ⭐ 新建门：`check-fake-signal`

> 这是**唯一**能根治五类的门。其余工作（§1）都是逐个案例。

### 2.1 检出规则（保守优先：宁可漏报 ⛔ 不可误报）

| 规则 | 检出对象 | 判据 |
|---|---|---|
| **R1 常量写入** | `pub f: bool` 赋 `true/false` 字面量 | 字段名匹配 `*_ok`/`*_safe`/`*_compliant`/`*_valid`/`*_healthy` **且** 无其他赋值点 |
| **R2 伪探测** | `fn detect/probe/measure*` | 函数体内零系统调用标记（`sysctl`/`Command::`/`/proc`/`cpuid`/`target_os`/`uname`/`std::fs`） |
| **R3 字面量实参** | `compute(true, x, true, true)` 形态 | 加权/评分函数的**实参为布尔字面量** |
| **R4 无测量证据** | `no_stall`/`cadence` 类字段 | 字段名含 `*_ok`/`*_stall`/`*_cadence` **且** 全仓无对应测量变量（`last_tick`/`tick_gap`） |

### 2.2 强制约束（写门时的硬要求）

| 要求 | 理由 |
|---|---|
| ⛔ 每条规则**必须有探针**（注入变异 → 必须报警） | 否则是「报 PASS 却结构上不可能失败」的门（R-SCAN-3 / L8 教训） |
| ⛔ 必须**分账**：baseline 记录既有 + `--strict` 只挡新增 | 存量 5 处已知，逐个裁决 |
| ⛔ 必须**排除注释与字符串**（复用 `nt_topology.py` 的 `_strip_noncode`） | 裸 grep 会误报（本仓把禁词当数据持有） |
| ⛔ 必须**排除 `#[cfg(test)]`**（花括号配对，非 split） | `check-unwrap` 已踩过此坑 |
| ✅ 必须输出**`file:line` + 证据行** | 审计要能追溯到现场 |

### 2.3 注册与探针

```sh
scripts/check-fake-signal.sh          # 门
scripts/probes/check-fake-signal.sh    # 探针：4 条规则各注入一次变异
```
注册进 `check-gate-satisfiable` 门表（当前 **22** 个 → 23 个）。

## 4. ⛔ 必须先修正的一处**不实记录**

`DEBT-LEDGER-2026-10-07.md` 现写「元门：恒红 **0**」。

**实测（2026-10-07）恒红是 3 个**：

| 门 | 实测输出 | 归因 |
|---|---|---|
| `check-layout.sh` | 新增 1 = 根目录 `notes/` | 工作区产物，⛔ 非代码缺陷 |
| `check-truth-surface.sh` | `UNCOMMITTED_DEP` × 2（`nt_run_trace.rs`） | **他窗 WIP**，⛔ 非本仓缺陷 |
| `check-doc-drift.sh` | root-doc deadlink **24 known** | 存量基线内 |

⇒ ⚠️ **本仓教训原文**：「陈旧门记录会让下一个 agent 去『修』正确代码，比没有门更危险」。

⇒ **门环境性红 ≠ 门坏**。`check-gate-satisfiable` 自己写着：
> 「两种可能，必须二选一：① 门真的坏了 → 修门；② 存量债已记账 → 搬进 baseline」

⇒ 而这三条**都不是这两种** —— 是**第三种**：**工作区状态**。
⇒ **T13 的正解是把这三种成因写进门自身**，让 `--strict` 能区分。

## 5. 执行纪律（照抄结论，不照抄数字）

1. **⛔ 无定点不改** —— 每个案例必须读那一行本身。
2. **⛔ grep 只找候选，不下结论** —— 走 `nt_topology.py` 或 `nt_locate --component`。
3. **⛔ 同名 ≠ 同一符号** —— 本会话已撞 **5 次**（`CapabilityVector`/`EvolutionForecast`/
   `SocialPath::standard`/`PlannerExecutor::verify`/`hybrid_search`）。
4. **⛔ 不凭字段名猜所属类型** —— 本会话撞 2 次（`started`/`shutdown_coordinator`
   都在父类型 `BackgroundLoop` 上）⇒ **编译器比推理可靠**。
5. **⛔ 猜数据结构必然错** —— 本会话 7 次 ⇒ 一律用真实构造器或 `Default::default()`。
6. **✅ 改门必须有对照实验** —— `git stash` 前后比数字。
   （`nt_security_wiring` 我曾**两次**提交零效果的"修复"，靠对照才发现。）
7. **✅ 反复失败 = 切面选错的信号** —— 触发**换切面**（改调用方/改字段类型/删函数），
   ⛔ 而不是试第 5 版。
8. **✅ 外部吸收只取概念、零代码复制** —— 本会话 7 个外部仓库，可直接复用的代码 **0 行**。
   有效落地（`memvid` 帧校验和）也是**用本仓已有 FNV-1a 重写**。
9. **✅ 提交只 `--only` 显式路径** —— 共享工作区，⛔ 禁 `git add -A`。
10. **✅ Cargo 串行** —— 16G 机器，⛔ 禁并行重构建，⛔ 禁 `cargo clean`。

## 6. 本方案的**已知局限**（诚实标注）

| 局限 | 说明 |
|---|---|
| ⛔ `check-fake-signal` 会有**误报** | R1 的字段名启发式（「名字像结论」不总成立）⇒ 必须 baseline + 人工复核 |
| ⛔ **查不出「真算了但算错」** | 伪信号门只判「是否计算」，⛔ 判不出「计算是否正确」⇒ 需交叉评测（另立项） |
| ⛔ R2 依赖**平台标记词** | 换平台写法（如 `sysctl` 换成 FFI）⇒ 漏报 |
| ⚠️ §1 五类处置**不能自动执行** | 每个都需要「这个字段声称自己是什么」的判断 ⇒ 逐个读现场是**不可省**的 |
