# 「我推演过」不是「我验证过」—— 2026-09-29 一个会话的 12 次未验证断言

> 本档记录**方法论**（可迁移的教训），不记录具体改了什么。
> 规约条目见 `AGENTS.md` 三道闸与 `RUST-STANDARDS.md` §17。
> 与同目录另五档的区别：那些讲单次事故或别的根因，本档讲**一条**：
> **验证义务在压力下悄悄退化成了推演义务**。

## 元教训

**本轮我做了 9 处「静态审查修掉的编译错」，把这当成 diligence 写进了交接文档。**

那 9 处是真的（`Option::ok()` 不存在、`?` 用在非 `Result` 函数、`MutexGuard`
当 `bool`…）。但**它们一个也没被编译器确认过**——因为内存门连续 BLOCKED，
按规矩没跑任何 cargo。于是同一份交接里同时存在两句话：

> 「静态审查有效」 ／ 「唯一下轮入口是编译」

第一句是我自己给自己发的**许可证**：既然手推抓到了 9 个错，那"没抓到的应该很少吧"
就成了默认假设。**这个假设没有任何依据。** 手推能抓到的错误类别是**有限的、
可预见的**（类型不匹配、API 误用），抓不到的是**语义错**（算法对不对、
坐标算得准不准、扫描到第几页时 `continue` 的语义）。我在 16 个单测里写的
断言**一个都没跑过**——而单测断言的期望值（`norm[0] == 118`）正是最需要
实测确认的那种数字。

**根因不是懒，是「验证」这个词被偷换了宾语。**
「验证过内存门」是验证；「推演过代码」长得像验证，因为它们共用「我主动查了」
这个外部特征。R-SCAN-1 已经说过「扫描器告警必须先读现场证实或证伪」——
**本档是它的自指版本：把「自己的推理」当成了权威。**

## 1. 能力断言：看签名 = 翻车（本轮 1 次，第二次同型）

**症状**：为"补齐文字定位缺口"做方案时，我差点写「`nt_world/ocr` 有
`OcrResult.bounding_boxes` 字段，可用于定位」。读下去发现
`PaddleOcrEngine::run_inference` 返回的是**空 vec 的占位**。

**根因**：`grep -n "bounding_boxes"` 命中的是**字段声明**，不是能力。
这与 2026-09-28 那次「`nt_jev` / `nt_crystal_core` 导出 ≠ 调用」**同型**，
第二次了。

**机械化**（能力型断言的通用判据）：

```sh
# 「看起来有能力」的类型里，配一对「占位特征」grep：
grep -n "bounding_boxes: Vec::new()\|todo!()\|unimplemented!()\|启发式\|占位" <file>
```

命中即**当场证伪**，不许写进方案当既有能力。

## 2. 提方案前先查「我们已经有了什么」

**症状**：用户问「自有技术能否补齐缺口」，我的第一反应是**装 tesseract**
（用户当场否决：「移除装 tesseract，减少外部依赖」）。改查后发现
`lopdf 0.42` 早已在依赖里，PDF 侧根本不需要新依赖。

**根因**：「缺口」是从**上游**清单推出来的，不是从**本仓**推出来的。
提「装 X」之前没做那一步 grep。

**机械化**：

```sh
# 提「引入/安装 X」之前，先证明 X 不在依赖树里、且没有等价的自制物：
grep -n "^<crate>" */Cargo.toml Cargo.toml
grep -rn "<能力关键词>" --include="*.rs" | grep -v "mod tests"
```

**通则**：方案的第一行不该是「装什么」，该是「我们已经有什么」。

## 3. 手推的产出不是证据，是**债务的重新分布`

**症状**：手推修掉 9 处编译错后，我在交接里写「静态审查有效」。

**根因**：把「发现问题的能力」误当成「问题已穷尽的证据」。真实关系是：
手推把**确定性错误**清掉了，**语义风险原封不动**。

**机械化**：交接文档里凡出现「已修 N 处」而**没有编译证据**，必须同句写明
「仍未编译」。两句话缺一，就是给下一个人发了假许可证。

## 4. 共享脏树里 `git add` 必须逐路径

**症状**：工作树里有 **61 项他人 WIP**（含 `Cargo.lock`）。一个 `git add -A`
就会把别人的半成品卷进我的提交。

**机械化**：

```sh
git add <逐个路径> && git diff --cached --name-only | wc -l   # 必须 == 预期数
git status --porcelain | wc -l                                # 剩余项 = 别人的，原样不动
```

本轮 13/13 对上，才提交。

## 5. 删入口 ≠ 删覆盖

**症状**：`/mcp call` 带着 4 个测试，其中一个**顺带在测 MCP 会话真 framing**。

**根因**：把「测试名字属于被删对象」当成了「测试只测被删对象」。

**机械化**（删任何东西之前）：

```sh
grep -rn "<被删符号>" --include="*.rs" | grep -v "mod tests"   # 覆盖是否在别处
```

本轮查到 core 侧 `test_native_adapter_drives_session` 测的是同一套握手，
才敢删。**删入口前先证明覆盖在别处；删完再 `grep -c dead_code`。**

## 6. 测试 fixture 自己造，别用环境里恰好存在的文件

**症状**：若拿仓库里某个 `.pdf` 当 fixture，测试会因「环境里恰好有那个文件」
而变绿；别人环境没它就红。**假绿比不绿更贵。**

**机械化**：fixture 在**同文件内**用字节构造（本轮手写 xref 生成最小 PDF，
`make_pdf` + `stream_obj` 算 `/Length` 长度）。顺带抓到自己把 `/Length`
硬编码成 43（实际 35）——而 lopdf 照 dict 里的 Length 切流，数字错会把
`endstream` 吃进 content。**fixture 里的一切长度都必须算出来，不许写死。**

## 7. 用户授权 ≠ 记录义务可以省略

**症状**：用户说「提交你的文件，不用编译」。我照做了——但立刻发现自己该
保留的那句"未编译"如果只存在于我的脑子里，**下一个人会把 `ab1b9d96`
当成已验证的代码**。

**根因**：把「决策权」和「记账义务」捆在一起了。授权改变前者，不改变后者。

**机械化**（提交后自检）：

```sh
# ⚠️ 判据本身实测失败过一次 —— 别照抄第一版。
# 第一版是 `grep -c "未编译\|未验证"`，结果对本轮**合规**提交 ab1b9d96 返回 0：
# 因为实际写的是「未经编译验证」「未跑任何 cargo」「未过：cargo check」——
# 语义齐全，词表不匹配。**固定词表判据会假阴性，而假阴性比没判据更坏**
# （它让人以为「没记录」，实际记了；下次就会真的不记）。
git log -1 --format=%B | head -3          # 约定：未验证须写在首行，人工确认语义
git log -1 --format=%B | grep -nE "编译|cargo|test" | head   # 至少"提到"这件事
```

**通则**：判据要查**语义要点**（有没有提、是不是否定），不要查**固定措辞**；
凡是「用 grep 守纪律」的规则，**必须先拿真实反例跑一遍**——包括拿自己刚写的
合规内容跑。本轮就是这么抓到的。

本轮第 2 条真抓到了：handoff 写着「刻意未提交」，提交完就是假话，已单独补
一个 commit 校正。**让文档随事实漂移，比让代码不带测试更危险。**

## 8. 收尾自查的最后一格：自检工具也会骗你

**症状**：本档第 7 条的机械化判据（`grep -c "未编译"`）对本轮自己的合规提交
返回 **0 命中**。第一反应是「提交信息漏写了」——第二反应才是「判据写错了」。

**根因**：把**措辞**当成了**语义**的代理。这与第 1 条同型（把字段名当能力），
只是方向相反：**过度相信**自己的判据。

**机械化**：任何自检命令，在**采纳之前**先拿「一个已知合规的样本」跑一遍，
确认它返回预期值。返回 0 时先怀疑判据，再怀疑对象。

**通则**：**判据的失败模式要和对它要检查的对象一样被严肃对待。**
一把坏尺子量出来的「合格」，比不量更危险。

## 收尾自查（本档的机械化清单）

```sh
rustfmt --edition 2021 --check <本轮新增/改动的文件>   # 比对 HEAD 基线，只算新增 hunk
git show HEAD:<file> | rustfmt --check | grep -c "^Diff in"   # 存量 hunk 数对照
python3 scripts/ops/nt_lock_audit.py <src>             # 改了 .rs 必须重跑
git diff --cached --name-only | wc -l                 # 提交面 == 预期数
```

**通则**：`rustfmt` 的存量债会让「整个文件不干净」变成常态，
所以比**基线 hunk 数**而不是看有没有输出。

## 9. 测试的**区分力**要靠变异验证判定，绿不等于有效（本轮 3 条测试骗了我）

本轮为「注册表快照序列化确定性」写了 3 条单测，**每条都读起来完全合理**。
把它们依赖的 `sort_json_keys` 改成**空操作**（即还原缺陷）后重跑：

```
test result: ok. 3 passed; 0 failed     ← 全绿
```

**零区分力。** 根因：同一进程内同一个 `HashMap` 的迭代顺序是稳定的，
而我挑的 3 个 key（`zeta`/`alpha`/`mid`）在这台机器上恰好恒为字母序。
⇒ 我挑的 fixture **恰好落在缺陷测不出的区域**。

**规约（硬）**：
1. 写完「防回归」测试，**必须做变异验证**：把被测的那一行改成空操作/删掉接线，
   确认**精确报红**。没报红 ⇒ 这条测试不测任何东西，删掉或重写。
2. **挑 fixture 时要主动选最难的那个**，别挑能过的。本轮正解：输入改用
   `serde_json::json!`（`preserve_order` 下**保留我的插入顺序**）⇒
   「输入逆序、输出必须有序」变成确定性的，把排序函数掏空必然报红。
3. 本轮有**第三类**同类陷阱：legacy 判别逻辑我**在测试里重抄了一遍**，
   生产代码改成恒真后测试照样全绿。⇒ **判别逻辑必须抽成唯一函数供测试调用**，
   绝不能让测试持有第二份实现。

## 10. 跨进程缺陷：单进程测试**结构上就抓不到**

同一个缺陷（`HashMap` 迭代序泄漏进文件），我确认它**真实存在**的方式是：
起 5 个独立进程跑真二进制 ⇒ **5 个互不相同的 md5**。而任何单进程测试都测不到。

⇒ 唯一判据是**跨进程**的（脚本或门）。
已落地 `scripts/ops/nt-registry-determinism.sh`（起 5 次独立进程比字节 + 断言
节点/边数零丢失），并已接 CI。
⛔ 别试图用「同输入序列化两次比对」—— 那是本轮**第一版**的错误做法，恒真。

## 11. 门自身会骗人，且**失败时返回 0 比没有门更坏**

自写的那个门第一次跑：内部因 `$var` 后紧跟全角括号触发
`unbound variable` 而中途死掉，**而我看到的 exit code 是 0**。

⇒ 一个会误报 PASS 的门比没有门危险：它训练人忽略报警。
**规约**：新门第一次跑完必须**故意制造一次失败**（或用变异验证），
确认它**真的会红且 RC≠0**，才算装好。
（本轮第二道防线：故意退回未修复代码跑门，得到
`FAIL: 第 2 次输出与第 1 次字节不同` + RC=1，才敢接 CI。）

## 12. 配置静默不生效 = **假成功**，且它看起来和成功一模一样

给 `.cargo/config.toml` 加 linker 配置，第一版三元组写成
`x86_64-apple-darwin`（本机是 `aarch64-apple-darwin`）⇒
**配置完全不生效**，而 `cargo build` 照样打印 `Finished ... in 0.39s`。

⚠️ 危险之处不是它失败，而是它**伪装成成功**——若我当时没核对「有没有真的重编」
，就会写下「lld 配好了」的假结论。

**规约**：
- 改 `rustflags`/构建配置后，构建**必须真的重编**；秒 `Finished` ⇒ 没生效。
- 目标三元组用 `rustc -vV | grep host` 取，**不靠记忆、不靠目录名**。
- 改构建配置后**必须跑一次门 + 测试**，确认产出的二进制功能正常
  （本轮：`cargo test -p nt_core_capability_tree` 54 绿才敢提交）。

## 13. `author` 字段**不能用来区分窗口**

本仓所有提交的 `author` 都是 `openhands`，**包括我自己的**。
我曾用 `git log --format=%an` 判断某个失败是「他窗引入」的——
那个结论恰好对，但**理由是错的**（靠的是文件清单，不是 author）。

⇒ 归属必须靠可复现的判据组合：
① 我的提交改了哪些文件（`git show --stat`）；
② 时间先后；
③ **不调链接器也能复现的判据**（本轮：`cargo check` 同样失败 ⇒ 与 linker 无关）。
⛔ 作者名是最弱的证据 —— 同一仓多 agent 共享 git identity 时它恒定。
