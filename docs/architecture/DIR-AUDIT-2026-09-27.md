# 目录架构审计 — 2026-09-27

> 范围：16 个 workspace 包 + 根目录 17 个散落文件 + 8 个根目录。
> 全部数据 2026-09-27 实测（`cargo metadata` / `git ls-files` / `du` / `grep`），非文档转述。

## 结论先行

**目录架构与「主代码进化之路」基本不契合。** 三条结构性错位，按危害排序：

1. **依赖方向被目录位置掩盖** —— 1 个 workspace 包物理嵌在另一个包的源码树里，2 个包是纯孤儿，1 个带 `unsafe` 的 FFI 包被 6 个 crate 依赖。
2. **8 类公共类型重复定义**（最坏 `SearchResult` × 9）—— 能力吸收一直在做加法。
3. **根目录同时存在 4 条路线图 + 2 套待办 + 3 份规则文件**，且有 0 字节垃圾文件与指向已删目录的陈旧 gitignore 规则。

**但真正的风险不是"乱"，是 `ARCHITECTURE.md §1-§12` 与 `§13` 互相矛盾** —— 前者描述的 C4/分层设计与后者描述的 neobot 融合不是同一个系统。调试时会一直在找不存在的东西。

## 一、16 个包的依赖拓扑

实测（`grep -E '^(neotrix|nt)[a-z0-9_-]* = ' <pkg>/Cargo.toml`）：

```
                        ┌─ neotrix-types（纯叶子，6 个包共用）✅
                        ├─ neotrix-sysctl（叶子，6 个包共用）⚠️ 唯一带 unsafe
                        │
neotrix-consciousness ←─┤
        ↑               │
neotrix-gateway ←───────┤   （依赖 consciousness + decision-engine）
        ↑               │
neotrix-reasoning ←─────┤
        ↑               │
neotrix-multi-agent ←───┤   （依赖 5 个，是条链的顶端）

neotrix (core) → 上述 5 个 + neobot + nt_core_capability_tree + types + sysctl
neotrix-tauri  → neotrix + neobot + nt_core_capability_tree
neobot-desktop → neotrix-neobot
neotrix-game   → neotrix-abilities
```

叶子包（无内部依赖）：`neotrix-types` `neotrix-sysctl` `neotrix-decision-engine` `neotrix-neobot` `neotrix-audit` `neotrix-abilities` `nt-lang` `nt_core_capability_tree`

### 缺陷 1：包的位置倒置了依赖方向

`nt_core_capability_tree` 是 workspace 成员，但物理路径在 **`crates/nt-core-capability-tree`** —— 嵌在 `neotrix` 自己的源码树里。而：

- `neotrix` 依赖它
- `neotrix-tauri` 也依赖它

于是出现 `neotrix-tauri → nt_core_capability_tree`（物理上在 `neotrix` 体内）**与** `neotrix → nt_core_capability_tree` 并存。**目录结构在暗示"它属于 neotrix"，而实际两者是平级包。** 52 个调用点散在 22 个文件里，这个歧义会持续误导定位。

→ 应移至 `crates/nt-core-capability-tree/`。

### 缺陷 2：`nt-lang` 是纯孤儿

- **零依赖者**：实测 `grep -rn "nt-lang" --include=Cargo.toml .` 只命中自身 manifest
- 5 文件 / 273 行
- **只有 `[[bin]]`，没有 `[lib]`** —— 结构上不可能被复用

它作为 workspace 成员被 `cargo check --all-targets` 编译、检查，却不产出任何可被消费的东西。

### 缺陷 3：唯一的 `unsafe` FFI 包被 6 个 crate 依赖

`neotrix-sysctl`（"macOS/Linux 系统指标读取专用 FFI crate"）是**全仓唯一带 `#![allow(unsafe_code)]` 的包**。而它被 `neotrix` / `consciousness` / `reasoning` / `gateway` / `multi-agent` **全部依赖**。

即：**平台相关的 unsafe FFI 铺满了 L5 认知层。** 分层设计上，L5 认知不该依赖系统指标 FFI。`types` 也是 6 包共用，但它是纯类型叶子（无 unsafe）—— 这才是正确的共用层形态。两者的差别正是问题所在。

### 缺陷 4：所谓「L5 四个平级 crate」其实是一条线性链

四者描述都写 "L5 …"，但依赖是严格线性的：

```
consciousness → gateway → reasoning → multi-agent
```

`multi-agent` 依赖 5 个包，`reasoning` 依赖 4 个。**它们不是平级的层，是 4 个子层伪装成平级包。** 后果：无法单独替换或独立测试其中一层，因为下层是上层的编译前提。

## 二、跨包同名类型 —— 逐对核实后的结论（2026-09-27 修正）

### 关键教训

**同名 ≠ 同类型。** 初版把「同名计数」当「重复计数」，差点把两个不同设计硬合。
`Skill`（带 `reuse_count`/`total_reward` 的已演化实例）与
`SkillDefinition`（带 `tier`/`entry_point` 的声明清单）就是活例子。

**`pub` 项不触发 `dead_code` lint**，所以零消费者的 `pub` 结构体可以静默存在很久。
发现死代码只能靠「精确路径 grep + 逐个排除同名异物」，不能靠 lint。

## 五、与「主代码进化之路」的契合度判断

**契合的部分**（应保住）：

- 6 层分层（`l0_substrate` → `l6_meta`）在**目录层面**是真的，文件数与 LOC 分布合理（l5 最大 224k 行，l0 最小 20k 行）
- `neotrix-types` 作为纯类型叶子被 6 包共用 —— 这是正确的共用层形态
- `neotrix-neobot` 是干净叶子，被 3 个上层消费而不反向依赖任何 L5 —— 产品线边界清楚
- 提取出的 4 个 crate（consciousness / reasoning / gateway / multi-agent）**已经是真实现**，非 0 字节空壳，并在 `l5_cognition/mod.rs:124-157` 作为 L5 公开 API re-export

**不契合的部分**（阻碍进化）：

| 症状 | 对进化的实际阻碍 |
|---|---|
| 8 类类型重复 | 加任何能力都要在 N 处同步改一遍 → 吸收速度随重复数线性衰减 |
| 4 个 orchestrator 并存 | 无法确定"新编排逻辑写在哪"，每次都要先做决策考古 |
| 包位置倒置（`nt_core_capability_tree`） | 定位工具与人类都被路径误导，`nt_locate.py` 索引里它与 `neotrix` 混同 |
| `unsafe` FFI 铺满 L5 | 任何"加固 L5"的安全工作都会牵连平台相关 FFI，无法独立审计 |
| 4 条路线图 + 2 套待办 | 下一个 agent 不知道该信哪本 —— 这正是本轮 `AGENTS.md`「0 命中」错误记录能存活这么久的土壤 |
| §1-§12 与 §13 互相矛盾 | 「设计图不反映现实时，调试会一直在找不存在的东西」（`ARCHITECTURE.md §16` 原话） |

**总体判断**：目录结构本身（6 层 + 提取 crate）方向正确，但**执行层欠收敛**。当前状态下增加能力，边际成本高于设计预期 —— 这与 `TODO.md:26` 把注册表收敛标为 PARKED 是同一现象的表征。

**建议顺序**：P0（3 项，依赖正确性）→ P1 第 5 项（`neotrix-types` 包内自重复，零风险）→ P1 其余 → P2 → P3。**P3 虽排最后，但 P0-P2 每完成一项就该同步更新一次，否则文档偏差会立刻重新扩大。**

**却没有一条接进生产决策点** —— 这是 R-P79（外部技术必须同会话接到生产可用）
的未清偿项。接线应先于装饰。

**方法论留痕**：`nt_decision_engine.rs` 曾被我判为「有 `mod` 导出即在生产」而
险些被当作活路径。**导出 ≠ 调用**；`pub mod` 只是 API 可见性。下刀前必须查
*构造点*（`::new(` / `new(`），而不是查 `mod` 声明。

### 6.1 附带发现 · `truth-surface` 门本地会把他窗 WIP 误判为 `UNCOMMITTED_DEP`

主工作树下 `bash scripts/check-truth-surface.sh --strict` → **exit=1, 3 offenders**，
一度被读成「已提交代码引用未提交文件 = fresh clone 不能构建 = CI 红了」。
**用 `git worktree add --detach` 建干净 HEAD 检出实测推翻**：

- 干净 HEAD：**exit=0, 0 offenders** ✅ → **CI 是绿的，无生产缺陷**
- 3 个 offender = `neotrix-neobot/src/{nt_changes.rs, nt_workspace.rs, nt_store/nt_store_changes.rs}`
  （均为 `??` 未跟踪），而声明它们的 `lib.rs` / `nt_store/mod.rs` 是**他窗未提交的 `M`**

成因：该门用 `git ls-files` 取 tracked 集，但读的是 tracked 文件的**工作树内容**，
故把他窗 WIP 里的 `mod X;` 当成了「已提交代码的声明」。**只影响本地信号，CI 干净
检出恒为 exit=0，不影响门禁价值。** 已决定暂不改动（避免动别人正在写的文件）。
**方法论**：门在本地报红 ≠ 门在 CI 报红；判定前先造干净检出实测（R-P16 精神）。

### 7.1 为什么本地全绿而 HEAD 坏

24 个报错文件中 **13 个已被另一窗口在工作树里修改**（`nt_io_awareness_core.rs`
的坏 import：工作树 0 处 vs HEAD 2 处）。**主工作树因含他人未提交修复而
「看起来正常」** —— 这是本轮最贵的一课，也是新门的存在理由。

### 7.2 新门：`scripts/check-fresh-build.sh`

`check-truth-surface.sh` 只扫 `mod X;`，结构上抓不到「已提交 manifest 引用
未入库文件」「`include_str!` 数据文件」「HEAD 内容陈旧」。新门直接回答
「干净克隆能构建吗」：

- **tier 1（`--metadata`，秒级）**：`cargo metadata` —— 抓 workspace member /
  `[[bench]]` / `[[bin]]` / `[[example]]` 缺文件。**本次 P0 前两处正是它该抓的**。
- **tier 2（`--full`）**：加 `cargo check --lib -p neotrix` —— 抓内容陈旧。
- **oracle 选择**：`CI=true` 或干净树 → 就地跑；脏树 → 自建
  `git worktree add --detach HEAD` 并在退出时清理。**脏树不是合法 oracle。**

**回归证明（非空门）**：在修复前的 `5fcb291b` 上跑 tier 1 得 exit=101，
报出 `failed to load manifest for workspace member apps/neobot-desktop`
—— 即本仓历史上一直是绿的那处断裂。

已接入 `.github/workflows/ci.yml` `check` job 的**第一条检查**（manifest 坏掉时
后续步骤都无意义，且秒级可测）。tier 2 与既有 `cargo check --lib -p neotrix`
同源，故 CI 不重复跑，门在本地作诊断用。

### 7.3 收口结果（2026-09-28 全部实测通过）

| CI 步骤 | 命令 | 干净检出结果 |
|---|---|---|
| ci.yml:24 | `cargo check --lib -p neotrix` | **exit=0** |
| ci.yml:25 | `cargo check -p neotrix`（全部 bins） | **exit=0** |
| ci.yml:42 | `cargo test --lib -p neotrix --no-run` | **exit=0** |
| 新门 | `scripts/check-fresh-build.sh --full` | **PASS** |

**修复方式不是新写代码，而是把早已写好却未入库的工作落盘**。逐层剥离取证：
每轮只把「报错文件里已完成的修复」放进独立 worktree 再重跑，直到收敛。三个
关键判断：

1. **工作树能编译 ≠ 可独立提交。** 拷入 `entry/mod.rs` 会拉进 `dialog.rs`，
   后者需要 `neotrix-neobot` 依赖，而 HEAD 的 `Cargo.toml` 没有 —— 错误数
   因此从 2 **反弹到 58**。必须把 `Cargo.toml` 一并纳入。
2. **M 版本不一定比 HEAD 好。** `nt_crystal_core/cocoons.rs` 的 M 版本自身
   带 E0597 借用错误（半重构），拷入即引入新错 → 回退到 HEAD 并排除。
3. **半成品绝不能进历史。** 排除 `cocoons.rs` 与 `nt_premise_selector.rs`
   （取证期间正被另一窗口编辑）；提交用「worktree 内提交 + `git update-ref`
   CAS 推进分支 + 主树 `git reset` 同步索引」，全程不碰他窗在制品。

唯一由我改的代码：`nt_graph_index.rs:340`
`a.out_neighbors(&fwd1[0])` → `a.out_neighbors(fwd1[0].as_str())`
（`out_neighbors(&self, id: &str)` 收 `&str`，而 `fwd1: &[String]`）。

### 7.4 第 4 个 blanket 规则：`models/`

门在**全绿状态下仍抓到 1 个错误**，由此暴露 `.gitignore:21` 的 `models/`：
`include_str!` 是**编译期**读取，被它引用的 `models/training/jev_platts.json`
不在 git 里 → 任何新鲜克隆都编译不过。

关键在于**静默**：`git add` 对被 blanket 通配跳过的文件既不报错也不提示，
所以「文件存在」与「文件入库」的落差可以潜伏任意久（本例从建仓至今）。
`models/` 实测 3.4GB（safetensors/onnx/pt），忽略它是对的，故**只精确解禁**
`models/training/`（`!models/` + `models/*` + `!models/training/`），
已验证 `model.safetensors` / `RealESRGAN_x4plus.onnx` 仍被忽略。

至此 blanket 通配伤人共 4 例：`tests/` `examples/` `benches/` `models/`。
前 3 例是源码，第 4 例是**数据** —— 后者连「源码存在性」类门都看不见。
