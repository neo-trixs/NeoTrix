# NT-Pack v1 — NeoTrix 高密度数据格式规范

**版本**: 1.0.3 | **域归属**: NT-MEMORY (知识守护者) | **设计者**: NT-CORE (des-architect)

## 设计目标

以最小数据量表达最高数据信息密度。面向 NeoTrix geo_index 这类"大量小记录"（每条 = 坐标 + 短字符串标签 + ID），目标对比基线：

| 基线格式 | 每记录字节 | NT-Pack 目标 |
|---------|-----------|-------------|
| GeoJSON 文本 | ~300-500 B | ≤ 12 B |
| Geobuf (protobuf) | 30-60 B | ≤ 12 B |
| FlatGeobuf | 64-106 B | ≤ 12 B |
| 单条 protobuf | ~36 B | ≤ 12 B |

## 设计来源（吸收自调研）

| 技术 | 来源 | 用途 |
|------|------|------|
| E6 定点 + delta + zigzag + varint | Google Encoded Polyline / HERE Flexible Polyline | 坐标压缩（11cm 精度，~4-6 B/点） |
| StringTable 字典 | OSM PBF | 字符串标签字典化（低基数 → 索引 1-2 B/值） |
| 列式布局 | Apache Parquet | 同质性分组，编码器跨记录找规律 |
| zstd (FSE/ANS) 熵编码 | Meta Zstandard / Duda ANS | 可选收尾压缩层（比 LZ4 小 ~30%） |
| 精度-信息量纪律 | GPS 精度研究 (5位小数≈1.1m) | E5 默认、E6 可选，避免存储噪声 |

## 文件布局

```
┌─────────────────────────────────────────────┐
│ 魔数 "NTPACK01" (8B)  │ 版本 1 (1B) │ flags (2B) │ 记录数 (4B) │
├─────────────────────────────────────────────┤
│ 列描述段                                     │
│   每列: [1B 类型][1B 精度]                   │
├─────────────────────────────────────────────┤
│ 字符串段 (StringTable)                       │
│   [4B 条目数] + [4B长度 + UTF-8 字节]*       │
├─────────────────────────────────────────────┤
│ 坐标段 (lat/lng 交错列)                      │
│   E6定点 → 行内delta → zigzag → varint 流    │
├─────────────────────────────────────────────┤
│ ident 段 (node_id 列存在时)                  │
│   [varint prefix_idx] + [varint len + 字节]* │
├─────────────────────────────────────────────┤
│ 索引段 (每列每记录)                          │
│   [varint 字典索引]*                          │
├─────────────────────────────────────────────┤
│ [可选 zstd 压缩层: 坐标+ident+索引 整体]     │
└─────────────────────────────────────────────┘
```

> 注: 压缩层只压数据区 (坐标+ident+索引), 头部+列描述+字典保持明文可解析。
> 压缩格式: `[varint 压缩长度][zstd 数据]` — varint 支持 >64KB (v1.0.2 修复 u16 溢出 bug)。
> 文件尾 CRC32 (v1.0.3): 尾 4B = 前面全部字节的 CRC32 (FLAG_CHECKSUM 位声明), 解码校验失败报 "checksum mismatch (文件损坏)"。
> 向后兼容: 旧文件无 FLAG_CHECKSUM 位 → 跳过校验。

## 列类型 (1B)

| 值 | 类型 | 编码 |
|----|------|------|
| 0 | 坐标 lat | E6 定点 → delta → zigzag → varint |
| 1 | 坐标 lng | E6 定点 → delta → zigzag → varint |
| 2 | 字符串字典 | StringTable 索引 (varint) |
| 3 | u32 原始 | varint |
| 4 | f64 原始 | 8B 直接 (需高精度时) |
| 5 | node_id | 前缀入字典 + ident 原始字节流 (见下) |

## node_id 前缀拆分 (COL_NODE_ID)

高基数 ID (如 `geo:airport:KLAX`, 46K 条全唯一) 字典化是纯浪费——字典本身 974KB + 索引 2B/记录。
优化: 计算全部 node_id 的**最长公共前缀 (LCP)** 入字典 (1 条目), 剩余 ident 部分按
`[varint len][原始字节]` 写入独立 ident 段 (不字典化)。

- 机场数据 LCP = `geo:airport:` (14B), ident 平均 5B/记录 → 省 ~16 B/记录
- 混合来源 (airport/volcano/city) LCP 退化为 `geo:`, 仍正确 (仅省前缀)
- 解码: `node_id = dict[prefix_idx] + ident[i]`

## flags (2B, bitmask)

| bit | 含义 |
|-----|------|
| 0 | 启用 zstd 熵压缩层 |
| 1 | 坐标用 delta 编码 (默认开) |
| 2 | 启用精度截断 (按列精度字段) |

## 坐标编码细节

- **E5** (1.1 m, 消费级 GPS): 定点乘 1e5, int32 范围 -18000000..=18000000 (经度) ✓
- **E6** (11 cm, RTK 级): 定点乘 1e6, 经度 ±180e6 超出 int32 → 用 int64 或 E6 分列
- delta: `cur - prev` (按记录顺序, 地理邻近 → 差值小)
- zigzag: `(n << 1) ^ (n >> 63)` (i64) / `(n << 1) ^ (n >> 31)` (i32)
- varint: 7-bit 小端, MSB 续传

## 字符串字典细节

- 全量唯一值入 StringTable, 每值分配递增索引
- 记录内按 varint 存索引 (基数 < 128 → 1B, < 16384 → 2B)
- 支持多标签: tags 用逗号分隔后整体入字典 (OSM PBF 同策略)
- 字典索引 0 保留 = 空值

## 验证方法

1. 编码 geo_index 真实数据 (机场 46,278 条 / 火山 1,214 条 / 城市 117,189 条)
2. 与 JSON / GeoJSON / CSV 基线对比字节数
3. 解码回读验证无损 (E5/E6 定点量化容差内)
4. 断言: NT-Pack ≤ 12 B/记录, 相比 JSON ≥ 30x 压缩

## 实测结果 (机场 46,278 条, 2026-08-11)

| 格式 | 字节 | B/记录 | vs JSON |
|------|------|--------|---------|
| JSON | 8,077,681 | 174.5 | 1.0x |
| CSV | 4,467,894 | 96.5 | 1.8x |
| NT-Pack E5 (无压缩) | 1,759,521 | 38.0 | 4.6x |
| NT-Pack E5 + deflate | 1,354,811 | 29.3 | 6.0x |
| NT-Pack E5 + zstd (v1.0.2) | 1,355,410 | 29.3 | 6.0x |
| NT-Pack E6 (无压缩) | 1,811,995 | 39.2 | 4.5x |
| **NT-Pack 全量 183,125 条** | 7,050,949 | 38.5 | 4.6x |

- 解码无损: 46,278 条 node_id/country/city/tags/source 全等, E5 精度 0.000005° (~0.5m)
- node_id 前缀拆分 (v1.0.1) 使 E5 从 56.5 → 38.0 B/记录 (-33%)
- zstd 替换 deflate (v1.0.2): 压缩长度 u16→varint 修复 >64KB 溢出 (真实数据压缩后 1.35MB)
- **全量验证 (183,125 条, 12 来源, v1.0.2+)**: 38.5 B/记录, vs JSON 175.4 B/记录 **4.6x**, 全部解码无损
  - 混合来源 LCP 退化 (`geo:` 前缀) 正确工作 — 边界/海岸线等长 node_id 拉高 B/记录
  - 单来源 (机场 46,278 条) 29.3 B/记录 vs 全量 38.5 B/记录: 高基数字段 + 长 node_id 摊销差异
- **12 B/记录 目标达成路径验证 (机场 46,278 条, E5+zstd)**:
  | 场景 | B/记录 | 判定 |
  |------|--------|------|
  | A 8字段全保留 | 29.3 | ❌ |
  | B 去 tags | 21.4 | ❌ |
  | C 去 tags+city | **9.8** | ✅ ≤12 |
  | D 只留 node_id+坐标 | 8.3 | ✅ |
  | E 纯坐标 | 5.9 | ✅ |
  - 结论: 12 B/记录适用于"精简字段"场景 (node_id+坐标+country/region/source), 8 字段全保留不适用
  - tags 字典 333KB → 省 7.9 B/记录; city 字典 437KB → 省 11.6 B/记录

## 性能基准 (v1.0.3, release 模式, 模拟 5,000 条)

`cargo run --release -p neotrix --bin nt_pack_bench [N]`

| 操作 | 耗时 |
|------|------|
| encode E5 (无压缩) | 860 μs/op |
| encode E5+zstd | 964 μs/op |
| decode E5 (无压缩) | 1.39 ms/op |
| decode E5+zstd | 1.52 ms/op |

- 模拟低基数场景: E5 21.0 / E5+zstd **13.6 B/记录** (vs JSON 182.6 → **13.4x**)
- 编码 5,000 条 < 1ms, 解码 < 1.6ms — 适合实时加载
- 模糊测试: 100 轮 × 4 组合 (E5/E6 × zstd/no-zstd) 随机数据 roundtrip **全部无损**
